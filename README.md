# SQL Requirement DDL

`sql-requirement-ddl` 是一个将业务需求转换为可审查数据库 DDL 的 Codex skill，覆盖表、字段、索引、约束、注释和迁移风险分析。

## 使用方式

在 Codex 中显式调用：

```text
$sql-requirement-ddl 设计商品扩展表的建表 DDL
```

适用场景包括：

- 新建表和修改已有表；
- 新增、修改或约束字段；
- 主键、唯一索引、普通索引和关联设计；
- 业务需求到 SQL DDL 的转换；
- DDL 的预检查、执行后验证和回滚说明。

该 skill 用于生成和审查 DDL，不替代数据库变更执行授权，也不用于普通 `SELECT` 或仅针对数据行的 `UPDATE`、`DELETE` 请求。

## 核心流程

1. 明确数据库引擎、版本、业务实体、字段含义、必填关系、默认值、唯一性和查询模式。
2. 对已有数据库对象执行只读 schema 检查，核对表、字段、类型、默认值、注释、索引、约束、字符集、排序规则和存储引擎。
3. 检查 NULL、重复值、超长值、不兼容值和孤儿关系等可能阻止迁移的数据条件。
4. 设计满足需求的最小 schema 变更，遵循项目现有命名和生命周期约定。
5. 复核字段、主键、索引、约束和大表迁移风险。
6. 按预检查、DDL、变更后验证、回滚说明的顺序输出。

如果无法取得实时 schema，必须明确标注 DDL 未经过当前数据库核验，不得把模型、迁移、缓存结构或旧文档当作最新事实。

## 建表和字段规则

- 新建表不指定 `ENGINE`、`CHARSET`、`CHARACTER SET` 或 `COLLATE`；
- `NOT NULL` 字段必须有符合业务语义的显式默认值；自增列、生成列等数据库语法例外需要明确说明；
- 状态类字段优先使用足够范围的 `TINYINT` 或 `SMALLINT`，并在注释中记录已确认的取值含义；
- 文本字段优先使用符合业务长度的 `VARCHAR`，只有确实需要时才使用 `TEXT`；
- 核心表包含 `create_time` 和 `update_time`，时间类型遵循项目现有约定；
- 金额使用最小货币单位的整数，IP 地址按实际 IPv4/IPv6 需求选择存储方式；
- 不凭空发明枚举值、默认值、外键级联行为或业务命名。

## 主键和索引规则

- InnoDB 表优先使用 `id` 作为单一自增主键；
- 已确认的业务唯一性使用 `uniq_` 索引；
- 普通索引使用 `idx_` 前缀；
- MySQL 主键直接写 `PRIMARY KEY (...)`，不额外命名主键约束；
- 复合索引根据等值、范围、排序、连接和最左前缀查询设计顺序；
- 避免重复索引，通常将单表索引数量控制在七个以内；
- 只有在项目和数据库行为已确认时使用外键。

## 风险和安全边界

对于大表或生产表，说明锁表、重建、耗时、复制和兼容性风险，不在没有引擎与版本证据时声称操作是在线的。

除非用户明确要求，不生成删除表、截断表或不可逆数据转换。需要破坏性操作时，先给出影响预检查和可恢复路径。

生成 DDL 不代表获得执行授权。数据库变更执行前，需要重新确认目标数据库和受影响对象。

## 文件输出

已完成的需求 DDL 保存到：

```text
/Users/a0000/tools/SQL/
```

文件名格式为：

```text
<需求名称>_YYYYMMDD.sql
```

SQL 文件应包含适用的只读预检查、DDL、变更后验证、回滚语句或不可回滚原因，并在文件头记录审查日期和本地 DDL 审查结果。已存在的目标文件不能未经授权覆盖。

## 数据库连接

同一任务中的相关 schema 检查复用一个只读数据库连接。完成最终数据库检查后，立即断开所有使用过的 MySQL 连接；如果后续需要继续查询，再重新连接并在结束时再次断开。
